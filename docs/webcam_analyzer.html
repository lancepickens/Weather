Webcam Analyzer

Per-frame cloud cover from catalog stars detected vs predicted

Overview Webcam Analyzer

What it does in one paragraph

For each frame of a 12-hour overnight timelapse from a fixed-pointing AlertCalifornia camera, the analyzer (1) corrects small PTZ drift against a reference frame, (2) projects every above-horizon catalog star to its expected pixel coordinates at that frame's timestamp, and (3) checks each predicted position for a real point source. The per-frame ratio detected / expected rolls up to an hourly cloud score: 0 = clear, 1 = overcast.

Pipeline

The three stages are separate processes — not one combined command — because each has a very different cost and re-run cadence:

StageCostWhen to re-run
fetch ~210 MB / 12 hours (network-bound)Each new night
calibrate ~30 s plate-solve (CPU-bound, local astrometry.net)Only when the cam is repositioned
analyze ~0.1 s/frame (~70 s for 12 hours of 1-min frames)Whenever you want a new score, or re-tune detection thresholds

Stage 1 — webcam-fetch

AlertCalifornia exposes timelapse pools at fixed temporal resolutions (10sec, 1min, …) under cameras.alertcalifornia.org/public-camera-data. The URL shape was reverse-engineered from the public viewer; the WINDOW_TO_POOL map in fetch.py picks the right pool for each requested window so that a 12-hour overnight fits in roughly 720 frames.

Each downloaded JPEG is cached by its Unix-timestamp filename in .frames-cache/<camera-id>/<pool>/<ts>.jpg, so subsequent runs only fetch new frames at the head of the manifest.

Stage 2 — webcam-calibrate

Two artifacts are produced and stored in calibration.json:

  1. A per-column horizon row (horizon_y[x]), so the analyzer knows which pixels are sky and which are foreground.
  2. A WCS solution mapping (RA, Dec) → (pixel x, y) for any catalog star.

Horizon segmentation

segment_horizon() takes a vertical Sobel response on a mildly-blurred grayscale image (the horizon is the strongest consistent vertical gradient in this scene). For each column it picks the strongest gradient row, then applies a per-column median filter to suppress single-column outliers. The output is a length-W integer array horizon_y giving, for each pixel column, the row of the horizon line.

Crop-and-solve: working around the index range

The Axis-StarrCanyon1 camera has a ~65° FOV. Astrometry.net's default index-4115 series only solves scale ranges up to roughly 5–8°. Feeding the full frame to solve-field reliably fails.

The workaround is in calibrate.run_solve_field(): crop a 200×200 patch from the center (DEFAULT_CROP = (860, 100, 200, 200)) and solve only that patch with --scale-low 5 --scale-high 8. Then translate the solved WCS back to full-frame coordinates by shifting CRPIX1/CRPIX2 by the crop offset (_wcs_with_full_frame_offset).

full frame 1920 × 1080 ┌─────────────────────────────────────────┐ │ │ │ ┌─────────┐ ← crop (860,100, │ │ │ 200× │ 200,200) │ │ │ 200 │ │ │ └─────────┘ │ │ │ └─────────────────────────────────────────┘ solve-field on the crop (5°–8° scale, fits indices) │ ▼ WCS for crop space ──── shift CRPIX by (-860, -100) ───▶ WCS for full-frame space
Pitfall: NAXIS in WCS headers

_parse_wcs_fits reads only the listed float_keys and str_keys. It deliberately skips NAXIS/NAXIS1/NAXIS2 — coercing them to float triggers ValueError: Unknown format code 'd' for object of type 'float' deep inside astropy.wcs.WCS.

Stage 3 — webcam-analyze

Per frame, score_frame() runs four steps:

1. Foreground drift correction

estimate_drift() cross-correlates only the below-horizon region of the current frame against the reference (and only the central 60% of width, to skip edge artifacts and shrink the workload). Sky pixels deliberately do not participate — stars rotate sidereally over a 12-hour window, and including them would bias the correlation toward sidereal motion rather than the mechanical PTZ drift we want to recover.

The correlation is a hand-rolled nested loop over a small ±20 px search window, not scipy.signal.correlate2d — for this band size the full FFT-based correlation is much more expensive than the windowed dot product.

2. Catalog prediction

catalog.predict_visible() takes the frame timestamp, site lat/lon/elevation, and filters an 83-star list (bright stars with Vmag ≲ 3.3 in J2000 ICRS, sourced from Hipparcos/SIMBAD) to those above the horizon at that moment. The transform is done in one batched astropy.coordinates.SkyCoord → AltAz call — per-star transforms are an order of magnitude slower.

3. WCS projection

project_stars_to_pixels() reconstructs an astropy.wcs.WCS from the calibration header and runs world_to_pixel_values(ra, dec) on each predicted star. The recovered (dx, dy) drift is added back at detection time, so the WCS itself is never modified per-frame.

4. Point-source SNR test

detect_at_position(image, x, y) reads a small window around the expected pixel, takes the peak vs the local median, and normalises by the median absolute deviation. Above snr_threshold counts as a detection. The default window=9 is wide enough to absorb residual drift the cross-correlation missed without picking up neighbouring sources.

Why the local-median approach

An earlier version ran scipy.ndimage.median_filter on the whole frame to make a background image, then subtracted. Profiling showed that one call accounted for 4.5 of 5 seconds per frame. Since the per-window detector already does its own local-median estimate, the global pass was pure overhead. Removing it brought per-frame cost from ~5 s to ~0.12 s.

Tuned defaults — why they aren't the library defaults

The Axis-StarrCanyon1 cam points roughly horizontally. Empirically, catalog stars in its field of view sit between alt −19° and +18°. The library's natural defaults (designed for an upward-looking all-sky camera) immediately wipe out every catalog star and produce a constant cloud_score = 1.0:

ParameterLibrary defaultThis camWhy
--min-alt 10°0° Cam's max alt is +18° — anything above 10° leaves almost nothing.
--max-vmag 3.04.0 Cam is sensitive enough to catch Vmag 4 in clear skies. The bundled catalog tops out at ~3.3 (80 of 83 entries are ≤ 3.0), so passing 4.0 effectively means "use every catalog entry" — adds ~3 prediction targets above the 3.0 cap.
--snr-threshold 4.03.0 JPEG quantisation and a small detection window justify a less-strict cut.

If you point this analyzer at a different camera, expect to re-tune these. The convenience wrapper run.sh bakes them in: --min-alt 0 --max-vmag 4.0 --snr-threshold 3.0.

Score → hourly CSV

FrameScore.cloud_score is just 1 − detected/expected. analyze.aggregate_hourly() bins frames by local hour (default UTC−7 PDT) and takes the per-hour median of cloud_score across all frames in that bin — plus a 90th-percentile column so brief cloud bursts in an otherwise-clear hour aren't averaged away. The output CSV columns: 

hour_local, n_frames, median_cloud_score, p90_cloud_score,
median_expected, median_detected,
median_sky_mean, median_sky_stddev

median_sky_mean and median_sky_stddev are above-horizon-pixel brightness statistics: featureless cloud reads as low stddev with high mean (a glowing overcast), while a clear starry sky reads as higher stddev (point sources) and a lower mean.

How this calibrated the predictor

On 2026-05-14/15 the predictor (with ring-max only) reported extinction for every hour overnight at Coe. The Axis-StarrCanyon1 camera, at the same elevation, showed clear skies overhead with Vmag-3 stars detected through the entire window. Diagnostic cloud_score was around 0.2 from 22:00 to 05:00 PT — well below the 0.5 you'd expect if the site were actually under the deck.

That mismatch motivated the marine layer below flag. The thresholds UNDERCAST_CENTER_RH_MAX_PCT = 70 and UNDERCAST_CENTER_COVER_MAX_PCT = 30 sit at the upper edge of the center-cell readings on that confirmed-clear night. The fix preserves the conservative ring-max signal (still useful — it correctly describes cells below the site) while adding a positive signal for "you're above the undercast."

Running it

# Idempotent full pipeline: setup → fetch → calibrate → analyze
./webcam_analyzer/run.sh

# Skip the network step and re-analyze cached frames
./webcam_analyzer/run.sh --skip-fetch

# Force re-plate-solving (e.g. after the cam was repositioned)
./webcam_analyzer/run.sh --recalibrate

# Use a specific reference frame
./webcam_analyzer/run.sh --reference .frames-cache/Axis-StarrCanyon1/1min/1778830000.000000000.jpg

run.sh picks the median frame of the largest pool as the calibration reference, which for a 12-hour overnight window is roughly 2 AM local — darkest, most stars, lowest sky background.
